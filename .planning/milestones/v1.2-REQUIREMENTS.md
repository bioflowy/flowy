# Requirements: flowy v1.2

**Defined:** 2026-03-12
**Core Value:** WDL 1.2で記述されたワークフローをDockerコンテナ上で正確に実行できること

## v1.2 Requirements

Requirements for S3 object storage milestone. Each maps to roadmap phases.

### Storage Abstraction

- [x] **STOR-01**: Storage Backend interface defined in internal/storage/ with methods for file upload, download, JSON read/write, and directory operations
- [x] **STOR-02**: LocalBackend implementation wraps existing shared filesystem code behind the Backend interface with zero behavior change
- [x] **STOR-03**: All existing spectool tests (156/156) continue to pass after LocalBackend refactor

### S3 Backend

- [x] **S3-01**: S3Backend implementation supports file upload to S3 via AWS SDK v2 PutObject
- [x] **S3-02**: S3Backend implementation supports file download from S3 via AWS SDK v2 GetObject
- [x] **S3-03**: S3Backend supports multipart upload for files exceeding a configurable size threshold
- [x] **S3-04**: S3Backend works with MinIO via UsePathStyle and custom endpoint configuration
- [x] **S3-05**: Scatter task outputs use shard-indexed S3 keys to prevent key collision

### Path Resolution

- [x] **PATH-01**: cleanPath() in wdl/task/inputs.go preserves s3:// URIs without corruption
- [x] **PATH-02**: Input files with s3:// prefix are resolved via S3 backend regardless of default backend setting
- [x] **PATH-03**: Input files with absolute local paths (/mnt/...) are resolved via local filesystem
- [x] **PATH-04**: Input files with relative paths are resolved via the configured default backend

### Configuration

- [x] **CONF-01**: Storage backend type and S3 settings (bucket, endpoint, region) configurable in YAML config file
- [x] **CONF-02**: Default storage backend specified in config file (used when --storage flag is not provided)
- [x] **CONF-03**: User can specify storage backend per workflow via --storage CLI flag on flowy run/submit
- [x] **CONF-04**: TaskClaimResponse extended with storage addressing config (bucket, endpoint, prefix) for daemon

### Daemon Integration

- [x] **DAEM-01**: Daemon downloads S3 input files to local staging directory before container execution (localize)
- [x] **DAEM-02**: Daemon uploads task output files from local directory to S3 after container execution (delocalize)
- [x] **DAEM-03**: Daemon cleans up local staging files after successful S3 upload
- [x] **DAEM-04**: Daemon handles S3 upload/download failures with proper error reporting to server

### Testing

- [x] **TEST-01**: MinIO integration tests using testcontainers-go verify end-to-end S3 workflow execution
- [x] **TEST-02**: Integration tests cover file upload, download, and intermediate file passing via S3

## Future Requirements

### Performance

- **PERF-01**: Streaming I/O for large files without buffering entire file in memory
- **PERF-02**: Input file reference caching on daemon hosts (avoid re-downloading same reference files)

### Testing

- **TEST-F01**: Full spectool 156/156 conformance gate on MinIO backend (make spectool with S3)
- **TEST-F02**: S3Backend unit tests with mocked S3 client for CI without Docker

### Backends

- **BACK-01**: GCS backend implementation
- **BACK-02**: Azure Blob Storage backend implementation

## Out of Scope

| Feature | Reason |
|---------|--------|
| Pluggable backend registry | Go interface is sufficient; registry adds unnecessary complexity |
| Container-level S3 access | Daemon handles all S3 I/O; containers always see local paths |
| S3 credentials in TaskClaimResponse | Security risk; daemon uses own config/IAM role |
| HTTP(S) import resolution | Deferred to future milestone |
| S3 bucket validation at submit time | Nice-to-have but adds latency; fail at task dispatch |
