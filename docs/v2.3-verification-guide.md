# v2.3 動作確認ガイド

v2.3 マイルストーン「Managed File Labels & UX」で追加された機能の確認手順です。対象は以下です。

- `parameter_meta.label` による managed file label の自動生成
- label template の安全な pure-Go 評価
- managed file の `source_type` / `run_id` による provenance 表示
- Files タブでの source badge と originating run へのリンク
- Files タブでの検索・type filter
- Run Workflow ダイアログでの label-first managed file picker

## 前提条件

```bash
# サーバー・デーモン・UI を起動
make dev

# 停止するとき
make dev-stop
```

以下の前提で記載します。

- UI は `http://localhost:3000`
- API は `http://localhost:8080`
- 確認対象プロジェクトのスラッグは `test-project`
- `executor` 以上のロールを持つユーザーでログインできる
- v2.2 の Files タブと registry-based workflow 実行がすでに動作している

補足:

- Browser Upload / S3 URI / Server Path import の基本動作確認は `docs/v2.2-verification-guide.md` を参照してください
- 本ガイドでは v2.3 で追加した「見え方」「追跡性」「label template」周辺に絞って確認します

## 1. 確認用 workflow を用意する

`parameter_meta.label` の確認には、workflow input の string 値を使って label を作るサンプルがあると分かりやすいです。例として以下を使います。

```wdl
version 1.0

workflow managed_file_label_demo {
  input {
    String sample_id
    String original_name
    File reads
  }

  parameter_meta {
    reads: {
      type: "fastq"
    }
    aligned_bam: {
      type: "bam"
      label: "${sample_id}_${original_name%.fastq.gz}.bam"
    }
  }

  call make_copy {
    input:
      src = reads
  }

  output {
    File aligned_bam = make_copy.out
  }
}

task make_copy {
  input {
    File src
  }

  command <<<
    cp "~{src}" out.bam
  >>>

  output {
    File out = "out.bam"
  }
}
```

この例では、次の入力値を与えると:

- `sample_id = sample-001`
- `original_name = reads.fastq.gz`

出力 managed file の label は `sample-001_reads.bam` になる想定です。

### レジストリ登録

```bash
flowy registry push --project test-project --name managed-file-label-demo managed-file-label-demo.wdl
```

必要なら一覧を確認します。

```bash
flowy registry list --project test-project
```

**期待結果:**

- workflow が registry に登録される
- UI の Registry 画面から `managed-file-label-demo` が見える
- `latest` tag が付いている

## 2. `parameter_meta.label` の基本確認

### 2a. workflow 実行

1. UI で `test-project` の Registry ページを開く
2. `managed-file-label-demo` のエントリ詳細を開く

- Run が `COMPLETED` になる

1. Project Detail に戻る
2. `Files` タブを開く
3. 直近で追加された `aligned_bam` 相当の行を見る

**期待結果:**

- label が `sample-001_reads.bam` になっている
- 補助表示として実パスがその下に見える

## 3. label template の安全性確認

この機能は shell を呼ばず、限定された構文だけを pure Go で評価します。無効な template でも run completion が壊れないことを確認します。

### 3a. 無効 template の fallback 確認

確認用に、workflow の output metadata を以下のように変えて再 push します。

```wdl
parameter_meta {
  aligned_bam: {
    type: "bam"
    label: "${missing_value}.bam"
  }
}
```

その状態で再度実行します。

**期待結果:**

- Run は `COMPLETED` のまま成功する
- Files タブには出力が登録される
- label は template 評価結果ではなく basename fallback になる
  例: `out.bam`
- サーバープロセスが shell / subprocess を起動した痕跡は不要

### 3b. 対応演算子の spot check

必要なら、同じ workflow を少しずつ変えて以下も確認できます。

| template | 例の入力 | 期待結果 |
|----------|----------|----------|
| `${sample_id}` | `sample-001` | `sample-001` |
| `${original_name%.fastq.gz}` | `reads.fastq.gz` | `reads` |
| `${original_name%%.fastq.gz}` | `reads.fastq.gz` | `reads` |
| `${batch#batch-}` | `batch-07` | `07` |
| `${batch##batch-}` | `batch-07` | `07` |

補足:

- v2.3 では full POSIX shell 互換ではありません
- 上表以外の構文を使った場合は成功よりも「安全 fallback」が優先されます

## 4. provenance 表示確認

v2.3 では managed file に `source_type` が付き、workflow-generated file には `run_id` も返ります。

### 4a. source badge の確認

1. `Files` タブに、少なくとも以下の 3 種類の file を用意する
   - workflow 実行で自動登録された file
   - Browser Upload した file
   - S3 URI または Server Path import した file
2. Files 一覧を見る

**期待結果:**

- workflow 由来は `Workflow` badge が出る
- Browser Upload 由来は `Upload` badge が出る
- URI / server path import 由来は `Import` badge が出る

### 4b. originating run link の確認

1. `Workflow` badge が付いた行を見る
2. **View run** をクリックする

**期待結果:**

- 対応する Run Detail ページへ遷移する
- `Upload` / `Import` 行には **View run** が出ない

## 5. Files タブの検索・filter 確認

### 5a. free-text search

1. `Files` タブ上部の検索欄に、対象 label の一部を入力する
   例: `sample-001`

**期待結果:**

- label に `sample-001` を含む行だけが残る
- path や file type に一致した場合もヒットする

### 5b. type filter

1. type filter で `bam` を選ぶ

**期待結果:**

- `Type = bam` の行だけが表示される
- free-text search と同時に使える

### 5c. no-match state

1. 検索欄に存在しない値を入れる
   例: `zzz-no-match`

**期待結果:**

- テーブル自体は壊れない
- `No files match the current filters.` が表示される

## 6. Run Workflow ダイアログの label-first picker 確認

### 6a. picker 候補の表示

1. `File` 型 input を持つ workflow の Run ダイアログを開く
2. managed file picker を開く

**期待結果:**

- 候補行の主表示が `label`
- その下に補助表示として `path`
- v2.2 の `file_type` ベースの候補絞り込みは維持されている

### 6b. 選択後の trigger 表示

1. picker から 1 件選ぶ

**期待結果:**

- 閉じた後の picker trigger でも label が主表示される
- 補助表示として path が見える
- 実際にフォームへ入る値は従来どおり path のまま

### 6c. manual path fallback

1. picker を使わず、下の手入力欄に直接 path を入れる
2. 実行する

**期待結果:**

- 従来どおり manual path でも実行できる
- picker は表示改善であり、manual path を置き換えてはいない
